# 未知构建与平台适配

版本号不作为入口条件。这个流程接收没有历史记录的安装包，在当前任务内分析是否能沿“定位并调整本地机型资格分支”的思路适配。它不是任意安装包的通用补丁，也不承诺每个候选都有可修改的限制。

## 先看实际程序

1. 用 `scripts/inspect_candidate.py` 做只读格式探测；指纹是本次文件的标识，不与一个允许列表比较。
2. 检查包来源、签名和内部结构。自解压 EXE 的外层架构不一定是其驱动或客户端架构；ZIP/XAR/DMG 容器也不能说明内部应用的平台。已有解包证据可复用，不重复安装工具或运行目标来“识别”。
3. 对应用目录或脚本式安装包，使用可用工具静态查看清单、脚本及内层二进制。无需把目录包强行传给只接收普通文件的探测脚本。
4. 区分机型资格判断、真实硬件依赖、操作系统/ABI 不匹配、授权登录和服务端访问控制。这个 Skill 只处理已定位的本地机型安装门槛；缺少驱动或不支持的系统不能通过改一个判断补齐。

## 两种系统、不同架构分别分析

| 候选 | 如何推进 | 不能据此推断 |
| --- | --- | --- |
| Windows x86/x64 | 分析实际 PE、安装脚本或托管入口，重新定位分支及调用路径 | 版本号相近或出现相同报错就具有同一偏移、指令或参数 |
| Windows ARM64/ARM64EC | 分析实际指令架构和混合模块，分别检查客户端、服务和驱动 | x64 应用能仿真运行就代表 x64 内核驱动能工作 |
| macOS Intel/Apple Silicon | 只有用户提供实际候选产品包时才进入分析；检查 Mach-O 切片、安装脚本、签名及系统扩展 | 存在与 Windows 产品功能一致的官方 macOS 发行版；Windows 补丁或安装参数可复用 |
| 未识别格式/包装层 | 继续静态识别、解包或检查脚本；缺少工具时说明具体需要 | 文件后缀就是架构，或未知格式可直接修改 |

Windows ARM 的内核组件需要 ARM64 版本，应用仿真不能代替驱动兼容性。见 [Microsoft：How emulation works on Arm](https://learn.microsoft.com/en-us/windows/arm/apps-on-arm-x86-emulation)。

macOS Universal 程序可以包含独立的 `x86_64` 与 `arm64` 切片，需分别定位实际执行路径。见 [Apple：Building a universal macOS binary](https://developer.apple.com/documentation/apple-silicon/building-a-universal-macos-binary)。识别到 Mach-O 不等于确认它适用于 macOS；还需检查目标平台与包内容。

## 取得能解释改动的证据

使用当前可用的原生/托管/安装包分析工具。REA、Ghidra 或其他反汇编工具是可选分析手段，不是已知样本使用者的固定安装依赖。没有相关工具时，明确缺少的能力，不宣称探测文件头已经完成逆向。

至少记录：

- 本次文件指纹、格式、目标系统/架构及具体分析对象；
- 机型不支持提示或结果的引用位置，以及通往拒绝/放行路径的调用与控制流；
- 条件值的来源、分支后状态初始化、栈与寄存器约定，证明不会跳过必要初始化；
- 哪些前置系统/硬件检查仍保留，哪些逻辑尚未确定；
- 实际安装入口、参数与有效载荷结构；不要假设有 `/S`，也不要运行未知安装器的“帮助”参数来当作静态分析；
- 本次服务、驱动、系统扩展与重启需求，是否具备目标系统可用的实现。

文本搜索、同名函数、字节模式或相似版本只能帮助定位，不能单独证明补丁语义。没有确认机型分支时停止修改，但保留已完成分析和具体缺口；不是因为版本号不在表中而拒绝。

## 为本次候选生成局部适配

在用户工作目录保存计划和必要的局部脚本，不改写仓库中旧样本的常量来“放行”：

1. 以实际分析结果生成本次修改：对象/切片、位置、原指令、替换指令、跳转目标和理由。按该架构编码并反汇编验证，不把 x64 字节移植到 ARM 或 Mach-O。
2. 绑定本次分析的原文件指纹及预期原字节，防止执行时换成另一个文件。这是防止改错文件，不是要求它匹配过去版本的白名单。
3. 只写独立副本，拒绝源/输出冲突和覆盖已有无关文件。验证原包未变、副本长度/布局符合计划、所有差异都能解释；压缩容器或签名元数据变化也必须记录。
4. 明确原签名失效及平台会如何处理；不得伪造官方签名、关闭签名验证、Gatekeeper、SIP、Defender 或驱动安全策略。若系统阻止，报告执行受阻，不能以“实验模式”掩盖。
5. 针对本次文件整理实际安装命令和安装后核对方法，沿用当前授权继续；用户仅要求静态分析时不运行。不要调用固定 `Invoke-CompatibilityWorkflow.ps1` 安装未知构建。

若此候选已有证据证明无需修改即可按官方支持方式安装，使用该方式并如实记录“未修改”；不要为了保持流程一致而强加补丁。

## 安装后决定是否生效

按 `SKILL.md` 的验收层级执行。新样本用本次原包的内容和系统基线做核对，不能把旧版本文件哈希、服务名称或固定目录当成通用正确答案。

报告至少区分：

- **已分析，未安装**：例如用户仅授权静态准备，或当前没有匹配的目标系统。
- **安装受阻/失败**：保留真实阶段与原因，不能用关闭防护或循环重装代替诊断。
- **安装完成，功能未验收**：已落地但没有实际启动/设备证据。
- **部分功能通过**：逐项列出，账号登录成功不能证明所有信息同步。
- **本机目标功能通过**：仅限本次明确测试的功能与设备，不自动升级为跨版本/跨平台通用结论。

已有官方原包拒绝机型的运行证据可以复用，不为制作前后对照擅自再次运行原安装器。只有修改证据、安装结果与实际拒绝路径能够对应时，才明确写“本机机型限制绕过已验证”。

本流程改变的是接收和分析未知候选的方式。目前附带的确定性补丁及 Windows 安装包装器仍只有 5.8.1.130 的已验证样本；没有随包提供通用 macOS/Windows ARM 补丁。
