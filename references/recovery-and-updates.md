# 恢复、等待与更新

## 安装异常

先区分失败阶段：原包校验、副本校验、Windows 启动阻止、安装器退出、核心文件、服务状态、具体功能。任何阶段的成功都不能替代下一阶段证据。

安装器仍在运行或有未关闭的失败窗口时，停止并请用户处理该窗口。不要自动结束高权限进程或循环重装。记录现有状态与错误类别；需要新一轮安装时说明原因、重新检查基线与当前用户授权。

Windows UAC 和安全提示由用户本人处理。权限不足或执行被系统策略阻止时不要降低安全设置，不自动更改执行策略、Defender、SmartScreen、驱动签名策略或启动配置。

## 卸载与恢复边界

辅助脚本记录基线、执行授权安装并核对结果，不提供「一键全系统回滚」。小米电脑管家、MiService、虚拟设备驱动和任务有独立生命周期。正常卸载入口可以卸载对应组件，但没有验证过主程序卸载会恢复旧 MiService、驱动和所有设置。

需要恢复时，先比较安装前后记录并明确目标，再由用户选择产品提供的卸载入口或其已准备的系统备份。不要根据名称批量删服务、驱动、注册表或共享目录；这些组件可能被其他小米软件使用。若用户需要系统级回退，应在安装前自行采用适合其设备的系统备份方案，不能把本 Skill 的 JSON 记录说成备份镜像。

## MiDeviceService 长时间启动

在已研究的样本中，`MiDeviceServiceEntry.dll` 的 `OTA::UpdateStrategyManager::Init` 附近逻辑（VA `0x180BA6AC0`）要求产品名、特定格式的序列号和系统版本信息。失败后存在指数退避；观察到同一进程约 17 分钟后才从 `StartPending` 变为 `Running`。

这是一个已确认的特定样本路径，不是所有启动等待的统一诊断。遇到类似情况先记录等待和服务状态，提供有限次数的只读复查；不要为了通过检查伪造序列号、改服务超时或反复重启。状态变成 `Running` 也不证明 OTA 初始化成功。

## 更新能力的边界

管家主界面存在独立的软件更新入口，已定位到：

`设置 → 关于 → 检查更新 → check_update_state(app_id=35) → JsOTA → OTAService.CheckUpdate → UpdateBusinessCLRWrapper → 原生更新业务`

历史回调曾给出版本 `5.8.1.130`，与当前版本相同，因此界面返回「已是最新版本」。尚未证明该值来自实时成功的服务器响应，也没有完成更高版本的下载和安装验收。不要将这种提示写成「自动更新完整可用」。

MiDeviceService 的 OTA 策略还涉及应用、固件和驱动分支，不能笼统当成主程序更新。**不要伪造小米笔记本硬件身份来获取驱动、EC 或 BIOS 固件。** 当前 Skill 处理的是本地安装器中的机型资格分支，新构建需先定位实际逻辑。

## 新版本如何支持

未知安装包不因版本号或历史哈希不同而拒绝。保持原包，在当前任务内按 [未知构建与平台适配](adapting-builds.md) 继续静态分析：确认实际系统和架构、来源与签名、控制流、保留的前置检查、真实安装入口及服务/驱动差异，再形成该文件的修改计划。尚未定位可修改分支时不猜测写入，但应保留分析进展和具体缺口；无需用户因版本不同重新提出适配请求。

现有固定脚本不能通过只替换版本号或 SHA-256 来宣称支持。即使新版本同样出现「不支持设备」，具体分支和偏移也可能变化。新增版本重新证明修改范围，沿用已有安装授权在匹配的目标系统进行实机验收；有需要时使用 REA/Ghidra 或其他分析工具。已知快捷流程不依赖这些逆向工具。

安装后按本次官方有效载荷核对文件，分别记录安装完成、机型门槛、主界面启动及用户功能。未验证的更新路径仍标为未验证；一次适配成功不能推广成后续版本自动可用。Windows ARM 或 macOS 候选需要各自的程序与驱动/扩展支持，不继承旧 Windows x64 安装命令。
